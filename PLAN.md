# AgentCRM delivery plan

## Working agreement
For every slice, implement a usable workflow, challenge it against specific failure cases, resolve findings, then run acceptance tests before advancing. A failing check reopens that slice. Record completed checks and remaining manual verification separately in CHANGELOG.md. Keep public artifacts fictional. Keep plaintext login credentials outside the repository. Shipping target is a dedicated Railway demo service with persistent storage.

| Slice | Deliverable and implementation | Skeptical review and resolution gate | Acceptance evidence |
| --- | --- | --- | --- |
| 1. Client economics | Store currency as integer cents, rates as basis points, fee agreements by effective date. Calculate fixed, marginal and whole-month fees. Allocate receipts proportionally with optional overrides. Snapshot partner earnings and separate refunds. Calculate client-specific owner shares after referral earnings, allocated expenses and carried losses. | Challenge partial payments, penny rounding, multiple refund entries, rates over 100%, loss isolation, expense double counting and missing terms. Reject invalid entries before persistence. | Node tests for shared pool, tiers, independent rates, changing rates, partial payments, refund limits, split expenses and monthly loss recovery. |
| 2. Identity and storage | Serve a same-origin application. Keep a SQLite database on a durable disk, opaque expiring sessions, password verifiers and independent role flags. Seed an empty database exactly once. | Challenge cross-role views, unauthorized writes, request forgery, stale edits, repeated submissions, failed transactions and restart behavior. Verify permissions on the server. | Sign in as each synthetic user, compare visible records, submit allowed forms, reject forbidden writes and stale versions, verify database after restart. |
| 3. Sales and partner portal | Track referrals, contact details, follow-ups and stage history from referral through won or lost. Keep duplicate review in the admin workflow. Support partner preference requests and approve them in the agency view. | Challenge duplicate names, partner identity tampering, linking multiple introductions to the same client and partner-to-partner privacy. | Submit synthetic referral, advance stage, associate won deal with client, submit and approve a preference. Verify other partners cannot view it. |
| 4. Earnings and payouts | Provide client agreements, fee entries, receipt allocation, adjustments, partner statements, separate owner payouts and configurable monthly due day. Show individual and shared-pool methods and bank-independent external payment references. | Verify that posting a fee alone creates no commission and recording a payout does not reduce earnings twice. Prevent overpayments and refunds exceeding original receipt. | Reconcile seeded client, partner and owner balances, partial receipt and refund before and after an external payout. |
| 5. Owner and agency reports | Show client-specific owner participation, expenses, loss carryforward and residual reserves. Provide directory with separately managed Super User designation. | Challenge over-allocation, clients with different ownership, and an owner who participates in one client. Restrict global financial views to the agreed privileged roles. | Exercise ordinary owner, designated super user and combined admin/super roles. Confirm sums reconcile on client and aggregate reports. |
| 6. UI integration | Use Stitch desktop shell, dark teal actions, ledger tables, readable cards and responsive navigation. Apply form labels, explicit monetary units and keyboard focus. | Check narrow layouts, long names, empty lists, invalid amounts and action visibility by role. Compare working screens against reference designs. | Browse representative desktop/mobile routes. Record observed coverage and gaps. |
| 7. Release | Review release manifest, exclude credentials and local databases, upload via GitHub web interface, deploy dedicated Railway service, attach persistent volume and generate HTTPS domain. | Check built revision, process health, durable mount, session settings and login visibility. Recover build issues before declaring live. | Capture actual public URL, deployment outcome, remote health and logins. Report separately any tests run only locally. |

## Rollback and maintenance
Retain release history on main. For an application regression, redeploy the last known healthy revision against a compatible database. Before changing stored-record format, back up the volume and define a versioned migration and restore check. Keep test fixtures separate from live records. Record defects with the failing scenario, affected workflow, fix and test name. Only report a release as live after checking its HTTPS endpoint.


## Evidence and remaining release gates

1. Financial engine. Eleven domain tests verify calculation and workflow behavior. Re-run the tests after any change to amounts, dates, commissionability or payout rules.
2. Authentication and persistence. One HTTP integration test covers six identities and restart recovery with SQLite. An independent smoke check signed in using each delivered sample password.
3. Sales. The duplicate-referral test exercises two people referring the same prospect and linking both won deals to one client. Stage history records the originating stage and the decision.
4. Reporting. Compare each synthetic partner statement to the receipt allocation and each owner statement to the client ledger. Check the agency reserve after summing owner shares. Investigate any difference before promoting data.
5. UI. Login page inspected in the local browser. Full visual comparison of the authenticated routes against the 15 Stitch exports and mobile-device testing remain pending.
6. Release. Source, tests and documentation are packaged together. Upload credentials stay separate. When repository upload is approved, inspect the commit, deploy the selected repository, mount a Railway volume at /data, configure the HTTPS domain and exercise each role on the hosted service.
7. Operations. Capture the live revision, hostname, volume mount and last verified time in the changelog. After a redeploy, confirm persisted sample records and the six role boundaries. Treat live verification and UI acceptance as separate gates.
